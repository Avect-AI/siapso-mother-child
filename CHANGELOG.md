### Added

- Emergency numbers by country of use (SCRUM-55). Who to call shows the national emergency numbers of the country where the phone is used, in place of those of Senegal for everyone: `app/src/config/emergency-numbers.json` (CC BY 4.0) lists 24 African countries and France (for testing), each number with at least two sources and the date they were fetched, a number whose sources disagree or with fewer than two reliable sources left out with why, and the TEAM CHECK line. The country is found offline, with no network lookup and no location permission: the deployment file's new `country`, then the country chosen in Settings or on who to call (kept in the settings, locked too), then the region of the phone's language (`fr-SN`), then its time zone (`Africa/Dakar`), else unknown; France is never found from the phone. Who to call says "Pays : Sénégal" under the numbers with a quiet "Changer le pays"; with no country, or one with no number, "Appelez le numéro d'urgence de votre pays." and "Choisir le pays" first, never a guessed number. A new country screen (`#/country`) lists the countries with a search; the settings show the country. A production build warns about a `country` the file does not have, and about a country fixed with no number and no `emergencyNumbers`.
- Encrypted profiles on the shared phone (SCRUM-39, `docs/threat-model.md`, `docs/privacy.md`). The profiles, the history of their results and the saved contacts are sealed at rest with WebCrypto: each record written gets its own random 256-bit data key, the record is encrypted with AES-GCM under it (a random 96-bit IV per encryption, additional data binding the envelope version, the store and the record id), and the data key is wrapped with AES-GCM by a key that only the code gives. The code is worked out once per unlock (PBKDF2-SHA-256, 600 000 iterations, random 16-byte salt) and the output split with HKDF-SHA-256 under two labels: the check half is the stored verifier (version 2), the other half is the wrapping key, non-extractable and kept in the page's memory only while the session is open (`app/src/domain/crypto.ts`, `app/src/data/vault.ts`). In both modes the phone's one code wraps every data key. The key is forgotten at every lock (the two minutes, a page hidden more than two minutes), at the quick exit, at a lock or quick exit from another tab, at the forgotten-code erase and when another code is made; nothing about a profile is read or written while it is closed, and an unlock still being worked out when one of these comes opens nothing. A code tried on a verifier another tab made again meanwhile is tried on the stored one, never opened with the old one. What stays in clear: the settings (language, mode, end of the welcome), the verifier, the wrong-code count, the tabs' random marks, the random ids of the records, the profile id of each history entry, the number and the size of the records. The first right code after the update seals every profile, history entry and contact an older version kept in clear and stores a new verifier (new salt) in the same transaction, which keeps the plaintext and the old verifier whole if it fails or the tab closes (`app/src/data/migration.ts`); the code screen then says that the profiles could not be opened, nothing opens, and the code is typed again. Once a version 2 verifier is stored no legitimate record is in clear: a record in clear is never shown (left out, or the contacts said unreadable) and is deleted at the next unlock, never sealed; a code made on a phone from before codes existed stores its verifier and the sealed records in one transaction. Only the storage steps are timed, never the encryption; a write that does not end in time is aborted unless it committed, and the stored verifier then decides. A verifier made by a newer version of the app is not tried and counts no try. A verifier with fewer iterations than the app makes is made again the same way, every data key wrapped for the new key. The forgotten-code erase still deletes everything. On a profile that opens with its situations answered (saved, or answers given back after the code), the long-term situations are hidden behind one button ("Situations masquées : touchez pour les afficher") whatever is ticked, since one of them says HIV; on a result, a note on contraception shows at a tap, the situations the base does not read are one hidden section, and in accompanied mode the reminders are one hidden section that is always there (the IPTp reminder is left out for HIV with cotrimoxazole), so an HIV profile and a profile with no situation look the same before any tap, except when SP or amodiaquine is checked (the interaction card, at a higher level) ("Information masquée : touchez pour l'afficher"). The messages of SP with cotrimoxazole and amodiaquine with HIV treatments, which also fire on the situation alone, say it as a condition ("Si la femme prend du cotrimoxazole (Bactrim), ..."), a question for the clinical committee (`knowledge/README.md`, H-1). The pseudonym of a profile saved or deleted and the name of a contact saved never go on a history entry (marks only, the names in memory). End-to-end tests from the format before the update, and with "Quitter" in another tab while the first code is worked out: no pseudonym, situation, term, contact or typed text anywhere in IndexedDB, local or session storage, and everything works offline.
- Answers not saved at the auto-lock (live test round 1: a11y-auditor#1, privacy-coercion#4, midwife#6). The answers of the profile and contact forms are kept in the page's memory as they are typed, never stored, hidden while locked and given back to the same screen after the code, which says "Vos réponses sont revenues, mais elles ne sont pas encore enregistrées."; the quick exit, a lock from another tab, the erase, another code or leaving the screen drop them. While a form has answers not saved, a band warns 30 seconds before the auto-lock ("L'application va se verrouiller : touchez l'écran pour continuer.") with "Continuer"; any touch puts the lock off (WCAG 2.2.1).
- Voice input in the product search (SCRUM-31, `docs/voice.md`). A large microphone beside the search field, shown where the browser can record. Without an installed voice it opens the new voice screen (`#/voice`, also from the settings): French or Wolof with their size (Wolof offered first, the interface language chosen at first), the model and its licence, the advice to install once on wifi at the health post, then the install button, the only thing that downloads a voice pack, with a progress bar and a cancel; an installation cut short keeps its files to go on later or be removed; once installed, a removal asked twice; one voice at a time. Installed: a tap records (elapsed seconds, a pulsing ring that stays still under reduced motion, a cancel; it ends by itself at 8 seconds), "Je réfléchis..." while the model transcribes, then "J'ai entendu : ..." and the text goes in the search field: the candidates are those of a typed name and each is confirmed, nothing is added from the voice. No candidate: type the name or choose it from the whole list. A refused microphone is explained in words; every voice pack error has a plain message. The flow is a tested state machine (`app/src/domain/voice-flow.ts`), and the end-to-end tests run the built app with a mocked speech worker (say "nebeday", see Moringa, confirm it; airplane mode; no `voice/` request before the install button). `@siapso/speech`: a worker that does not answer within 180 s (about 1.5 times the 123 s measured with the CPU slowed 6 times) is terminated and replaced, `cancel()` stops what is pending, a pack loads once, the ONNX Runtime files must be in the voice cache before the pipeline is made, threads only in a cross-origin isolated page, and `installedVoicePackInfo`, `storedVoicePackBytes` and `removeVoicePackFiles` read and clean the Cache API without the network. The service worker is now the app's own (`app/src/sw.ts`, vite-plugin-pwa `injectManifest`): every page it serves is cross-origin isolated (COOP same-origin, COEP require-corp), so the model may run on several threads; the first visit stays on one thread. The speech worker's script (about 490 KB) is out of the app precache and budget: the service worker caches it only once a voice is installed, and an update that finds a voice installed caches the new script or does not install. The ONNX Runtime files of a pack live under `runtime/<version>/` and the manifest keeps the version, so a pack for another runtime reads as to install again (only the runtime files download). The model is freed 3 minutes after its last use and when the page is hidden, and uses at most two threads on a 2 GB phone. The licences screen loads apart from the first screen. About links to a new licences screen (`#/licences`) with the voice software, models and data and the full Apache 2.0 and MIT texts.
- Pre-publication audit (SCRUM-44, `docs/audit/2026-11-audit.md`). `sh tools/release/audit.sh` scans every commit of every ref, not only the working tree (`--published`: every branch, tag and pull request ref the remote serves, through a mirror clone): secrets with gitleaks 8.30.1 (downloaded at run time into the git-ignored `.cache/audit/` and checked against pinned SHA-256 values, never committed), licences with `reuse lint`, forbidden sources named in content, personal data patterns (Senegal phone numbers, email addresses other than placeholders, IP address literals, private key headers, cloud access keys and tokens) in files and commit messages, files over 1 MiB, key, `.env` and secrets file names, and the author and committer addresses by domain. It never prints a matched value, only the check, the kind, the path and the commit. Its fixture test (`tools/release/audit.test.sh`) runs in CI. The report lists every finding with its resolution, the decisions left to the team, and the steps to make the repository and the voice models public, which were not executed. Two decisions are applied: the JSON Schemas (`*.schema.json`) are now MIT like the code, and the impeccable design briefs (`app/.impeccable/**`) CC BY 4.0; `THIRD_PARTY_NOTICES.md` describes the origin of the impeccable font index.
- Signed knowledge packs and updates by fragment (SCRUM-38, `docs/pack-signing.md`, `docs/threat-model.md`). `siapso-pack sign` (`pnpm knowledge:sign`) adds `keyId` to `manifest.json` and writes `manifest.sig`, an Ed25519 signature of the exact bytes of the manifest (`@noble/ed25519` 3.2.0, `@noble/hashes` 2.4.0), with a key file (`--key`) or the `PACK_SIGNING_KEY` variable, and warns when `app/src/config/pack-keys.ts` does not list the key; `siapso-pack keygen --out <file>` (`pnpm knowledge:keygen`) writes a new key pair to a file outside every repository (links and Windows junctions resolved, the folder must exist) and prints the public key; `siapso-pack build` stays unsigned. The app checks the signature with the public keys of `app/src/config/pack-keys.ts` (committed empty: the team adds its key) before trusting the manifest; takes only a version strictly above the active one (semantic version order; the very same pack signed again is taken without a download) and never below the version of the pack built with it (`__MIN_PACK_VERSION__`), whatever the state of the phone's storage; downloads only the fragments whose sha256 changed; activates nothing before every fragment and the whole pack are checked; keeps the previous pack, and the storage checks the versions again in its transaction. In accompanied mode, once the code is given, the Status screen offers to go back to the previous version, with a confirmation, at once and without a reload; a rolled back version is not taken again. The Status screen says whether the base could not be loaded, a new base was refused (with the technical reason in accompanied mode) or the previous version was put back. A pack whose key was removed from the list is refused, the stored one included. `pnpm build` is now the demo build (Vite mode `demo`, `VITE_ALLOW_UNSIGNED_PACK=true` from `app/.env.demo`, into `app/dist-demo`, never `app/dist`): it accepts an unsigned pack, prints a warning, and shows "Version de test : base de connaissances non signée." on Status and About in every build that accepts unsigned packs. `pnpm release:build --key <file>` builds and signs the pack, makes the production build into `app/dist` and checks it; every build that does not accept unsigned packs refuses the flag in production mode, needs a listed key, and checks with the app's own code that the pack it ships is signed by a listed key. Every build writes `build-info.json` (mode, unsigned packs accepted, pack version and key, no secret). `minimum-safe-version` in `knowledge/pack.yaml` (optional, signed in the manifest as `minimumSafeVersion`) withdraws earlier packs: no rollback below it, and a pack rolled back to below the minimum safe version of the app pack is replaced by the app pack; it never decreases nor disappears (`pnpm knowledge:check` compares it with `origin/main`). CI makes demo builds only, checks that the release build stops with the signing refusal, and signs nothing. The service worker precaches `manifest.sig`.

- Lighter voice model, plan and scripts (SCRUM-42). Measured: 4-bit weights (`speech/convert/quantize_q4.py`, MatMulNBits, block 32, embedding in int8) shrink the Wolof model files from 298.7 MB to 207.8 MB and raise the FLEURS word error rate from 54.1 % to 57.1 % (100 sentences, Node); the French base pack goes from 110.2 MB to 83.0 MB and from 30.3 % to 32.1 %. The 100 MB goal is not reached by quantisation for Whisper small. Not run, needs a GPU and consented data: `speech/train/finetune.py` (Whisper base or tiny, licence gate, hashed `requirements.txt`), `speech/train/README.md` (data plan, consent, CNERS opinion, licences) and `speech/train/distill.md`. `lock.py` takes `--dir`; `pnpm eval:speech` takes `--dtype q4`.
- DHIS2 aggregate export (docs/dhis2.md, open-data/dhis2/): monthly counts per health district as DHIS2 dataValueSets JSON (period YYYYMM), no individual data. A cell is exported only with more than 10 checks, a count below 5 is not exported, and no omitted value can be recomputed from the exported ones (same feasibility rule as the open data). One immutable restricted file per month, 28 days after it ends (`<YYYYMM>-<release>-restricted.json` with a notice sidecar), written only to `open-data/dhis2/out/` or outside the repository and never published, to prevent cross-release differencing with the open weekly CSV. Identifiers come from a mapping file; the command refuses to run while a placeholder remains and the district list is left for the team to complete. The event format gains an optional district and iptpReminderShown.
- Evaluation API (`server/`, `docs/api.md`): a `node:http` service that runs the same engine as the offline app. `GET /v1/health`, `GET /v1/pack` and `POST /v1/evaluate` (`{ pack_version, context }`) with API keys stored as SHA-256 hashes and compared in constant time, a per-key fixed-window quota (in memory, per instance), a 16 KiB body limit, and answers 401, 429, 413, 415, 400 (error path, never the value) and 409 (pack version mismatch). The request schema refuses every unknown field, so no identifying data is accepted; unrecognised item text is at most 80 characters and is never logged or echoed. Logs hold method, path, status and latency only. An OpenAPI 3.1 document generated from the schema, a parity test that sends every reference case over HTTP and through the library, and a Dockerfile (Node 24 slim, non-root, health check; no image is built or published). `pnpm server:start` runs it.
