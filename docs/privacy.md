# Privacy on a shared phone

The app is often used on a phone shared by a family. A pregnancy, an HIV status or a contraception can be a secret there, so nothing about a profile may show without the code.

## Threat model

- **Covered:** casual access by someone else in the family who picks up the phone: they see no pseudonym, check, result, history, saved contact or mode without the code, in any tab of the app, and the quick exit hides everything at once, in every tab.
- **Covered since SCRUM-39:** someone who reads the browser's storage without the code (a lost or taken phone, the developer tools, a copy of the browser's files) reads nothing about a profile, its history or the saved contacts: they are sealed with a key that only the code gives (`docs/threat-model.md`, "Personal data on the phone"). What stays visible is listed below ("What the phone keeps").
- **Not covered:** a forensic attacker who copies the storage and tries every code offline: a code of 4 to 6 digits bounds the encryption (minutes on a graphics card for every 6-digit code, hours or days on a laptop), and the waits after wrong codes do not apply there.
- **The knowledge pack** (a tampered or replayed pack, a compromised signing key) is covered in `docs/threat-model.md`.

## What protects the data

- **The code:** 4 to 6 digits, never stored. A code among those someone else tries first (one digit repeated such as 0000, digits in a row up or down such as 1234 or 9876, a year from 1950 to 2030 such as a birth year) gets a plain warning and a second yes before it is kept: under the wait after wrong codes a person gets about 11 tries in the first hour, enough for the most common codes. It is not refused: a code she can remember matters more than a code she will forget, and the forgotten-code erase would then take her data. Only a verifier is kept: the code is worked out once per unlock with PBKDF2-SHA-256 (600 000 iterations, random 16-byte salt), and the output is split with HKDF-SHA-256 into the check, stored and compared in constant time, and the key that opens the data, never stored. A verifier of an older version (the PBKDF2 output itself, or fewer iterations) is made again with a new salt after the next right code, in the same transaction as the data it opens. There is one code on the phone: a code is stored only in a transaction that finds none, so a tab left on the welcome (the app opened twice, or a tab sent back to the welcome by an erase) can never make a second code over hers; it asks for the stored code instead, and says that a code already exists. A welcome cut short after the code was stored (the app closed) asks for that code, then for the mode. A new code opens the app only once storage shows it stored: a slow or failed write opens nothing. A new code's length is chosen first: 4 digits are offered for her own profile and 6 in accompanied mode, where one code opens the profiles of many women; the other lengths stay one tap away (SCRUM-56).
- **The code's length, in clear (SCRUM-56):** the length of the code (4, 5 or 6) is kept beside its verifier, so the code screen tries the code as soon as that many digits are in, with no "Ouvrir" to press ("Ouvrir" stays for a keyboard or a screen reader). Each such try is counted before the code is worked out, as every try: a wrong digit is a wrong code. A verifier kept before the length was keeps "Ouvrir" until the next right code adds its length, in the transaction that already sweeps the storage at an unlock, with the same salt and check (the code and every key stay as they were). What this shows: anyone who types digits on the code screen sees at which count the code is tried, so the code's length shows to someone who picks up the phone; and someone who reads the storage reads the length. It narrows nothing an attacker could not already try: someone at the code screen still gets 5 tries before the first wait whatever the length, and an offline search over a copy of the storage (out of scope, below) that tries the codes shortest first goes through every 4-digit code (10 000) before any longer one, so a 4-digit code falls in the same time with or without its length, and a 6-digit code still needs up to the 1 000 000 tries of its length (the 110 000 shorter codes it skips are about a tenth of the search). A length changed in the storage from outside only makes the code screen try at the wrong count, each try counted; editing the storage is out of scope (`docs/threat-model.md`). The team accepted this trade-off for one tap less at every opening (SCRUM-56, Q-T6).
- **Encryption at rest (SCRUM-39):** every profile, history entry and the saved contacts are sealed with AES-GCM, each record with its own random 256-bit data key, itself wrapped with the key the code gives; a random IV per encryption, and additional data binding the record's store and id (`docs/threat-model.md`). That key is held in the page's memory only while the code is open, and forgotten at every lock, at "Quitter", at a lock or "Quitter" from another tab, at the erase and when another code is made. The first right code after the update seals what the older version kept in clear and deletes the plaintext in the same transaction, with the new verifier (version 2); if that fails, nothing opens and nothing is lost, and the code is typed again. Once a version 2 verifier is stored, no legitimate record is in clear: a record in clear is never shown (a profile or a history entry is left out, the contacts are said unreadable, never listed) and is deleted at the next unlock, never sealed, so a number or a term written into the storage from outside never becomes hers. Only the storage steps are timed, never the encryption: a slow phone is never refused for being slow, and a write that does not end in time is aborted, unless it committed anyway (the app then opens with the new verifier). A code made by a newer version of the app is not tried, and no try is counted.
- **Wrong codes:** the fifth wrong code starts a 30 second wait, each further one doubles it, up to 30 minutes. The wait is said in minutes and seconds as it is read aloud ("1 min 59 s"). The count is kept in storage and shared by every tab of the app, and each try is counted before the code is worked out, so a second tab or a closed tab never gives free tries. A code screen open in another tab reads the count again when a try is counted and when it comes back, so it says how many tries are really left.
- **Locks:** at start, after two minutes without interaction, when the app comes back after more than two minutes hidden, and at once with "Quitter". While locked, the address is the neutral `#/unlock` and the screen that was open is held in memory only.
- **Answers not saved at the auto-lock:** the answers typed in the profile or contact form are kept in the page's memory as they are typed, never stored (not in IndexedDB, local or session storage, nor on the history entry), hidden while locked, and given back to the same screen once the code opens it again, which says they are not saved yet. "Quitter", a lock or "Quitter" from another tab, the erase, another code, or leaving the screen drop them. While a form has answers not saved, a band warns 30 seconds before the auto-lock ("L'application va se verrouiller : touchez l'écran pour continuer.") with "Continuer"; any touch puts the lock off, as WCAG 2.2.1 asks of a time limit. The answers typed for a passer-by ("Regarder sans enregistrer") are warned about the same way, but go with her at the lock: they are never given back after the code.
- **The lists of a visit (accompanied mode):** a relay goes from woman to woman in one compound. The unfinished list of each woman looked at waits while another woman is looked at, so it is not typed again; her row in the list of profiles says "Liste en cours". These lists stay in the page's memory only, never in storage nor on a history entry. Every lock of the tab forgets the lists waiting for the other women: two minutes without interaction, more than two minutes hidden, a lock from another tab, another code made in another tab. "Quitter" (in any tab), the forgotten-code erase and a reload forget every list, the one on screen included. Across a lock the list of the woman on screen stays: after the two minutes, the code brings her screen and her list back; after a lock from another tab, the code opens the start and her list comes back when she is chosen again. A deleted profile takes its list with it.
- **A passer-by ("Regarder sans enregistrer"):** in accompanied mode, a woman seen once (a sale at the depot) can be looked up without a profile. Her answers (pregnancy, term, breastfeeding, situations) and her list stay in the page's memory only: no profile, no pseudonym, no history entry, nothing in storage. They are shown in accompanied mode only, and she is let go: when another woman or another passer-by is looked at; at every lock of the tab (two minutes without interaction, more than two minutes hidden, a lock from another tab, another code made in another tab), after which the code opens the list of profiles, never her screen; at any change of mode; at "Quitter" (in any tab); at the forgotten-code erase; and at a reload. When her term has passed 42 weeks meanwhile, the check opens her questions again, never a profile. The browser history lists `#/quick` as it lists the other screens.
- **Sensitive answers on screen:** on a profile that opens with its situations answered (saved, or answers given back after the code), the long-term situations are hidden behind one button ("Situations masquées : touchez pour les afficher"), whatever is ticked: one of them says HIV, and hiding it alone would show through "Aucune de ces situations". The check says the situations answered for her the same way (SCRUM-56, so that a "none" ticked by reflex can be seen): one quiet "Situations" beside her term, the same for every profile and every passer-by, and only a tap shows "Situations : aucune" or the situations ticked, hidden again at every new showing of the check. On a result, a note on contraception (accompanied mode) shows at a tap only ("Information masquée : touchez pour l'afficher"); the situations the base does not read are said in clear (live test round 2, SCRUM-52: a health worker who did not tap read the result as covering a sickle cell disease it left out): the HIV situation is always read by rules, so it is never among them, and a test fails if a pack stops reading it (the section would then be hidden behind that button again, whatever it holds); and in accompanied mode the reminders are one hidden section that is always there, empty or not, since the IPTp reminder is left out for a woman with HIV on cotrimoxazole and its absence alone would say so. Its button says what it holds and nothing else ("Rappels : touchez pour les afficher"): a depot keeper or a relay knows a reminder is there without the screen saying anything of her (the decision of the encryption review, SCRUM-39, kept after the live test round 2). The result of an HIV profile and that of a profile with no situation look the same before any tap, except when SP (sulfadoxine-pyrimethamine) or amodiaquine (ASAQ included) is checked: the HIV profile then gets the card of the cotrimoxazole or HIV-treatment interaction, worded as a condition, at a higher level ("before the next dose" where the profile with no situation gets "unknown"), in both modes and at every state of the pregnancy, because the interaction is real. Someone who has seen SP checked for other women, with no such card, can infer her situation from it. This is a decision of the team: the rules stay, since removing them would harm women on cotrimoxazole and showing the card to every woman would discourage the routine preventive treatment of malaria (IPTp); the clinical committee is asked about it (`knowledge/README.md`, H-1). They are hidden again at every new showing of the screen. A finding is never hidden (a safety message): the two that also fire on the HIV situation alone, SP with cotrimoxazole and amodiaquine with HIV treatments, say it as a condition ("Si la femme prend du cotrimoxazole (Bactrim), ...", "Si elle suit un traitement du VIH ou prend du cotrimoxazole, ..."), never as a fact about her, a point left to the clinical committee (`knowledge/README.md`, H-1). The level of such a finding still shows that a rule fired.
- **Every tab of the app:** "Quitter", a lock asked for, the forgotten-code erase and a new code reach every open tab. A BroadcastChannel tells the other tabs at once; an epoch of random marks (nothing about a profile) is kept in local storage, whose change reaches the other tabs too (the storage event), and a copy in IndexedDB; every tab reads both again, and the stored code, when it gets the focus, shows again or comes back from the back-forward cache, so a tab that was frozen or cached when the message went out applies it before anyone reads it. Every tab then locks and forgets the screen it held; after the erase every tab goes back to the welcome, and a tab on the welcome moves to the code screen once a code is made elsewhere. An erase or a new code is followed only once the stored code shows it: a forged message or mark cannot fake them. An auto-lock stays in its own tab: each tab counts its own two minutes, and one in the background locks when it shows again after more than two minutes.
- **The danger signs answer of a check (SCRUM-56):** "no sign now" or the signs ticked are kept in the page's memory for one check only, so that adding or taking off a product does not ask them again. They are forgotten when the check screen is left (Back, the band's "Signes de danger", her profile, the list of profiles), when her answers change (her profile saved, the passer-by's answers changed), when another woman or passer-by is looked at, at every lock of the tab, at "Quitter" and at a reload; never stored, never on a history entry. Her history keeps one entry per check, with the highest level shown during it, so a danger shown once stays in her history even when the product is taken off; a passer-by's check keeps none.
- **History entries:** what a screen leaves on a history entry (a product searched or confirmed, a result's instruction and signs, the danger signs ticked, the profile or contact being changed) stays in the page's memory. The entry itself holds only random marks: the browser writes history entries to disk to restore a session, and a reload reads nothing back. What comes from a profile, and the danger signs ticked, are tied to the session's epoch, which changes at every lock and every page load; what the quick exit leaves behind is tied to the visit, which it renews. A product searched or confirmed, a profile id and a contact id never go in the address (`#/confirm/product`, `#/profile/edit`, `#/contacts/edit`). The pseudonym of a profile saved or deleted, and the name of a contact saved, which the next screen says once, go the same way: marks on the entry, the name in memory. At every lock, the entry of a screen behind the code is replaced by the neutral `#/unlock` with no state at all; the values the marks point to stay in the page's memory only (to give the held screen back after the code) until "Quitter", the erase or a reload.
- **Danger signs before the code:** the danger signs and who to call open without the code, so that nobody waits for a code in an emergency. What she ticks there is forgotten after two minutes without interaction or more than two minutes hidden (a new epoch starts while locked), at every lock and at a reload, and "Quitter" is offered on these two screens before the code too: one tap hides the signs and leaves the neutral screen.
- **Forgotten code:** the only way is to erase the profiles, their history and the saved contacts, after typing EFFACER and a last yes. The language and the knowledge pack stay. A profile, a check or a contact is written only with the code the tab opened: its verifier's salt and hash, kept at the unlock, are compared with the stored verifier in the same transaction as the write. A tab left open across the erase (one that missed every message) cannot write her data back, neither before the next code is made nor after. The mode and the end of the welcome in the settings are written under the same check (or, from a tab that opened no code, only while no code is stored); the language changes from any tab. A tab told of the erase also closes its database connection; the next use opens a new one.
- **Woman mode opens her own profile only:** a profile made in woman mode is marked as hers (`self: true`), one made in accompanied mode is not (`self: false`). Woman mode opens and checks for her marked profile, never another woman's profile kept on the same phone (a phone used in both modes); a record older than the mark is taken as hers only when it is the only profile.
- **Deleting one profile:** behind the code, "Supprimer ce profil" on the profile screen, then a last step ("Supprimer le profil {pseudonym} ?", which says the profile and the history of its results are erased from this phone for good), deletes that profile and every history entry of it in one IndexedDB transaction, written only with the code the tab opened, as every other write of profile data: nothing of hers is left, or nothing is removed. The other profiles, the saved contacts and the code stay. Her list, on screen or waiting, is forgotten; the lists of the other women stay. In woman mode she can delete her own profile the same way; the app then starts an empty profile of hers, even when profiles made in accompanied mode stay on the phone. A midwife or a depot keeper removes a woman who moved, left follow-up, or a profile made by mistake, without erasing everyone. The deleted records are no longer readable through the app; a copy of the browser storage taken before the deletion holds only their sealed form.
- **The voice:** the microphone opens only when its button is tapped, and closes when the recording ends (at most 8 seconds), is cancelled or the screen is left. The audio stays in the page's memory, goes to the speech worker on the phone and is dropped once transcribed: never stored, never sent, never played back. What was heard goes in the search field as if typed, and is kept no longer than a typed name. The voice pack is downloaded only by its install button on the voice screen; whether a voice is installed says nothing about a profile.
- **Typed fields:** the fields she types in (the pseudonym, the term and the ages, the search, the units, the contacts) ask the browser not to keep what is typed in its form history (`autocomplete="off"`), and the code field is a one-time code no password manager keeps.

## What the phone keeps

The inventory of the browser's storage for the app's origin (live test round 1, privacy-coercion#11), as someone who reads it without the code finds it:

- **IndexedDB `siapso`, store `profiles`:** one record per profile: its random id and the sealed profile (`{ id, sealed }`). Nothing readable: no pseudonym, term, date, situation or product.
- **Store `history`:** one record per result kept (20 per profile at most): its random id, the random id of its profile (the index that deletes it with her profile) and the sealed entry (`{ id, profileId, sealed }`). The products, remedies and names typed, the level, the rules, the danger signs and the date are sealed.
- **Store `contacts`:** one record, the saved contacts sealed (`{ sealed }`): no name, role or number readable.
- **Store `settings`:** the settings in clear (language, mode woman or accompanied, end of the welcome); the code's verifier (salt, check, iterations, version 2) and the code's length (4, 5 or 6, SCRUM-56), never the code; the wrong codes in a row and the end of their wait; the tabs' random marks.
- **Store `pack`:** the knowledge pack in use and the one before, public content.
- **Local storage:** the tabs' epoch of random marks (`siapso-session-epoch`), nothing about a profile.
- **Session storage:** a random mark of the visit (`siapso-visit`).
- **Cache Storage:** the service worker's copy of the app and the knowledge pack (and the voice pack once installed), nothing about a profile.
- **Cookies:** none.
- **Visible from it all:** the number of profiles and of results per profile, the size of each record, and the times at which the browser wrote its files.

## Limits

- **The phone's clock:** offline, the only clock is the phone's. Setting it forward ends a wait early; setting it back never stretches a wait beyond its length. A date set back before a day the app has already seen (the profile's last save, its last result, the knowledge pack's date) reads every term as unknown, the riskier case, and the result says why.
- **The recent apps screen** of the phone may still show the last screen as a thumbnail, and Chrome's tab switcher keeps the last frame of each tab of the app, taken before a lock in another tab reached it.
- **Two minutes hidden:** the app locks when it comes back after more than two minutes hidden, not at once: a midwife who opens the dialler or a message for a moment, or a relay who answers a call, comes back to the same screen without typing the code again. Within those two minutes, someone who picks up the phone right after she switched to another app sees the screen she left, and the thumbnail is not blanked. "Quitter" is the way to hide everything at once, and it is one tap on every screen once the code is given. This is an agreed trade-off (live test round 2).
- **A danger result and the lock:** a result left untouched locks after two minutes like any other screen, a danger result included: it names products that can tell a pregnancy, an HIV treatment or a contraception. Someone without the code then sees the code screen, whose band keeps "Signes de danger" one tap away, and from there who to call with the emergency numbers and "Allez au poste de santé maintenant.", all without the code; nothing of the result is said there. From a danger result, who to call also says the products of the danger ("Dites aussi ce qu'elle prend :"), only while the tab is open in the same epoch, as the signs: after a lock it says neither. After the code the result comes back as it was. This is an agreed trade-off: a longer wait on a danger result would leave her products on screen for anyone, and the danger path never needs the code.
- **A tab that hears nothing:** without the BroadcastChannel and without local storage (a browser that blocks site storage for the page), a tab still in sight, which neither gets the focus nor shows again, applies an exit, a lock or an erase of another tab only at its own two-minute lock. Its writes stay refused once the code it opened is gone.
- **Pseudonyms:** a pseudonym is used once on the phone (compared without case, accents or extra spaces) and has 40 characters at most; a longer one is refused with the limit said, never cut. The screen reminds that it is never the real name, but cannot tell a real name from a nickname.
- **The forgotten-code erase:** anyone who holds the phone can erase the profiles, the history and the saved contacts without the code, by typing EFFACER and a last yes, also during a wait after wrong codes. Nothing is revealed by doing so, and nothing tells her afterwards beyond the welcome screen she finds. This is an agreed trade-off: a woman who forgets her code must not lose the app for good, nor wait up to 30 minutes after her own wrong tries to start again, and the erase gives an attacker nothing to read. In a household where someone could destroy her record at will, the record is not a safe place for anything she cannot lose: the health worker's booklet stays the reference.
- **The erase and other tabs:** the erase does not upgrade or delete the database to send other tabs a `versionchange` event. An upgrade would need a new database version at every erase, and a deletion blocked by another tab stays queued and could run later, after the next person has made a code, and erase that person's data. The guarded writes above make a stale tab harmless instead.
- **The browser history:** the browser lists the addresses of the screens opened, with their times (for example `#/check`, `#/danger/call`). They name no product, no person and no id, and every page is titled with the neutral app name, but they show that a check took place. The app cannot remove them, and the erase does not: the browser's own settings do (History, then Clear browsing data). Since SCRUM-56 a check is one history entry, `#/check` (in woman mode her check is her start, `#/`, which tells even less): the search, the danger signs present now and the result are on that screen, so the history shows that the check screen was opened and nothing of its steps (the search screen, `#/search/<kind>`, still opens from it for a name it does not find or the whole list after the voice). The old addresses `#/signs` and `#/result` open the check.
- **Form history and session restore:** `autocomplete="off"` is a request; a browser may still keep what was typed. The session restore file keeps the addresses and the marks of the history entries, never their values. Both are files of the browser, outside what the app or SCRUM-39 encryption can reach.
- **The page title:** every screen keeps the neutral app name ("Carnet" by default, `app/src/app-name.ts`) as its title, never the name of the screen. The title is what the phone shows outside the app: in the recent apps screen and Chrome's tab switcher, in the browser history with the time, in a bookmark or a shared link, and read out when someone switches apps with a screen reader. A title such as "Résultat", "Mon profil" or "Signes de danger" there would tell anyone who picks up a shared phone that a pregnancy check took place, even after "Quitter". This is an agreed trade-off with WCAG 2.4.2 (Page Titled): inside the app, each screen says what it is in its heading, which takes the focus when the screen opens, so a screen reader user hears the screen's name at once; only the title outside the app stays neutral.
- **The danger signs on the neutral screen:** the band keeps "Signes de danger" one tap away on every screen, the neutral screen after "Quitter" included, because missing a danger sign is the worst failure (implementation design, section 2). Someone who opens it without the code sees the general lists, headed "Pendant la grossesse", "Après l'accouchement" and "Chez le bébé", which say what the app is about; no personal data is shown. This is an agreed trade-off.
- **About and the knowledge base before the code:** "Réglages", then "À propos" and "Base de connaissances", open without the code: they hold no personal data, and the intended use, the licences, the sources and the date of the knowledge base must be readable by anyone, a health worker checking the app or a woman who forgot her code included. "À propos" names the app (SIAPSO Mère-Enfant) and says it is for pregnant and breastfeeding women, so the neutral name "Carnet" on the home screen and in the band does not hide its purpose from someone who looks there; with the danger signs one tap away (above), the cover is a name, not a disguise. This is an agreed trade-off: hiding the intended use behind the code would hide it from the people who must be able to read it.
- **The key of the data** never comes from what is stored: the stored verifier is the HKDF check half of the code's PBKDF2 output, and the key is the other half. A verifier of the versions before SCRUM-39 was the PBKDF2 output itself; it is replaced, with a new salt, at the first right code after the update.
- **Plaintext left behind by the update:** the browser's storage engine may keep the records it replaced, in clear, in its files until it compacts them; a forensic copy taken soon after the update may hold them.
- **Records counted and sized:** the encryption hides what a record says, not that it exists, how big it is, or which profile a result belongs to (by random ids).
