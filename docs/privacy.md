# Privacy on a shared phone

The app is often used on a phone shared by a family. A pregnancy, an HIV status or a contraception can be a secret there, so nothing about a profile may show without the code.

## Threat model

- **Covered:** casual access by someone else in the family who picks up the phone: they see no pseudonym, check, result, history, saved contact or mode without the code, in any tab of the app, and the quick exit hides everything at once, in every tab.
- **Not covered:** a forensic attacker (someone who reads the browser's storage or files with tools). The profiles stay unencrypted in IndexedDB until SCRUM-39 adds encryption at rest; until then the protection is that the interface never shows them without the code.
- **The knowledge pack** (a tampered or replayed pack, a compromised signing key) is covered in `docs/threat-model.md`.

## What protects the data

- **The code:** 4 to 6 digits, never stored. Only a PBKDF2-SHA-256 verifier is kept (600 000 iterations, random salt, constant-time comparison). An older verifier with fewer iterations is made again at the full count after the next right code. There is one code on the phone: a code is stored only in a transaction that finds none, so a tab left on the welcome (the app opened twice, or a tab sent back to the welcome by an erase) can never make a second code over hers; it asks for the stored code instead, and says that a code already exists. A welcome cut short after the code was stored (the app closed) asks for that code, then for the mode. A new code opens the app only once storage shows it stored: a slow or failed write opens nothing.
- **Wrong codes:** the fifth wrong code starts a 30 second wait, each further one doubles it, up to 30 minutes. The count is kept in storage and shared by every tab of the app, and each try is counted before the code is worked out, so a second tab or a closed tab never gives free tries. A code screen open in another tab reads the count again when a try is counted and when it comes back, so it says how many tries are really left.
- **Locks:** at start, after two minutes without interaction, when the app comes back after more than two minutes hidden, and at once with "Quitter". While locked, the address is the neutral `#/unlock` and the screen that was open is held in memory only.
- **Every tab of the app:** "Quitter", a lock asked for, the forgotten-code erase and a new code reach every open tab. A BroadcastChannel tells the other tabs at once; an epoch of random marks (nothing about a profile) is kept in local storage, whose change reaches the other tabs too (the storage event), and a copy in IndexedDB; every tab reads both again, and the stored code, when it gets the focus, shows again or comes back from the back-forward cache, so a tab that was frozen or cached when the message went out applies it before anyone reads it. Every tab then locks and forgets the screen it held; after the erase every tab goes back to the welcome, and a tab on the welcome moves to the code screen once a code is made elsewhere. An erase or a new code is followed only once the stored code shows it: a forged message or mark cannot fake them. An auto-lock stays in its own tab: each tab counts its own two minutes, and one in the background locks when it shows again after more than two minutes.
- **History entries:** what a screen leaves on a history entry (a product searched or confirmed, a result's instruction and signs, the danger signs ticked, the profile or contact being changed) stays in the page's memory. The entry itself holds only random marks: the browser writes history entries to disk to restore a session, and a reload reads nothing back. What comes from a profile, and the danger signs ticked, are tied to the session's epoch, which changes at every lock and every page load; what the quick exit leaves behind is tied to the visit, which it renews. A product searched or confirmed, a profile id and a contact id never go in the address (`#/confirm/product`, `#/profile/edit`, `#/contacts/edit`).
- **Danger signs before the code:** the danger signs and who to call open without the code, so that nobody waits for a code in an emergency. What she ticks there is forgotten after two minutes without interaction or more than two minutes hidden (a new epoch starts while locked), at every lock and at a reload, and "Quitter" is offered on these two screens before the code too: one tap hides the signs and leaves the neutral screen.
- **Forgotten code:** the only way is to erase the profiles, their history and the saved contacts, after typing EFFACER and a last yes. The language and the knowledge pack stay. A profile, a check or a contact is written only with the code the tab opened: its verifier's salt and hash, kept at the unlock, are compared with the stored verifier in the same transaction as the write. A tab left open across the erase (one that missed every message) cannot write her data back, neither before the next code is made nor after. The mode and the end of the welcome in the settings are written under the same check (or, from a tab that opened no code, only while no code is stored); the language changes from any tab. A tab told of the erase also closes its database connection; the next use opens a new one.
- **Typed fields:** the fields she types in (the pseudonym, the term and the ages, the search, the units, the contacts) ask the browser not to keep what is typed in its form history (`autocomplete="off"`), and the code field is a one-time code no password manager keeps.

## Limits

- **The phone's clock:** offline, the only clock is the phone's. Setting it forward ends a wait early; setting it back never stretches a wait beyond its length.
- **The recent apps screen** of the phone may still show the last screen as a thumbnail, and Chrome's tab switcher keeps the last frame of each tab of the app, taken before a lock in another tab reached it.
- **A tab that hears nothing:** without the BroadcastChannel and without local storage (a browser that blocks site storage for the page), a tab still in sight, which neither gets the focus nor shows again, applies an exit, a lock or an erase of another tab only at its own two-minute lock. Its writes stay refused once the code it opened is gone.
- **The forgotten-code erase:** anyone who holds the phone can erase the profiles, the history and the saved contacts without the code, by typing EFFACER and a last yes. Nothing is revealed by doing so. This is an agreed trade-off: a woman who forgets her code must not lose the app for good, and the erase gives an attacker nothing to read.
- **The erase and other tabs:** the erase does not upgrade or delete the database to send other tabs a `versionchange` event. An upgrade would need a new database version at every erase, and a deletion blocked by another tab stays queued and could run later, after the next person has made a code, and erase that person's data. The guarded writes above make a stale tab harmless instead.
- **The browser history:** the browser lists the addresses of the screens opened, with their times (for example `#/check`, `#/search/product`, `#/result`, `#/danger/call`). They name no product, no person and no id, and every page is titled with the neutral app name, but they show that a check took place. The app cannot remove them, and the erase does not: the browser's own settings do (History, then Clear browsing data). The steps of a check stay separate history entries because Back must work on every screen.
- **Form history and session restore:** `autocomplete="off"` is a request; a browser may still keep what was typed. The session restore file keeps the addresses and the marks of the history entries, never their values. Both are files of the browser, outside what the app or SCRUM-39 encryption can reach.
- **The danger signs on the neutral screen:** the band keeps "Signes de danger" one tap away on every screen, the neutral screen after "Quitter" included, because missing a danger sign is the worst failure (implementation design, section 2). Someone who opens it without the code sees the general lists, headed "Pendant la grossesse", "Après l'accouchement" and "Chez le bébé", which say what the app is about; no personal data is shown. This is an agreed trade-off.
- **The data key of SCRUM-39** must not reuse the verifier's derivation: the verifier is the PBKDF2 output itself and is stored, so a key equal to it or derived from it would be readable from storage. SCRUM-39 derives with another salt, or splits one PBKDF2 output with HKDF into a stored verifier part and a secret key part.
