# Threat model

This document lists what SIAPSO Mother-Child protects, against whom, how, and what it does not protect against. It covers the personal data kept on the phone and its encryption at rest (SCRUM-39), and the knowledge pack (SCRUM-38, details in `docs/pack-signing.md`). How the interface keeps a shared phone discreet (the code, the locks, the quick exit, the tabs) is in `docs/privacy.md`, with the inventory of what the browser's storage holds.

## What is protected

- **The alert levels.** The deterministic engine sets every level from the knowledge pack (rules, products, plants, danger signs, messages). A wrong pack can lower an alert for a pregnant or breastfeeding woman: its integrity and freshness are a safety matter.
- **Personal data on the phone**: the profiles (pseudonym, pregnancy and term, baby's age, long-term situations such as HIV with cotrimoxazole, products taken every day), the history of their results (products and remedies checked, names typed as unrecognised, danger signs ticked, level, rules, date) and the saved contacts (names and numbers of health workers). A pregnancy, an HIV status or a contraception can be a secret in the family that shares the phone.

## Personal data on the phone (SCRUM-39)

### Threats

- **Casual access on a shared phone:** someone in the family picks up the phone. Nothing about a profile shows without the code, in any tab (`docs/privacy.md`).
- **A lost or taken phone, or someone who reads the browser's storage without the code** (the developer tools of a desktop browser, a copy of the browser's files): they read nothing about a profile, its history or the saved contacts. The records are sealed with a key that only the code gives.
- **A changed record:** a byte changed, a record moved under another id or into another store, a wrapped key swapped between records. Every record is authenticated: one that does not open is left out (a profile, a history entry) or the contacts are said unreadable; a sealed record is never shown altered. A record in clear is never shown either once a version 2 verifier is stored (below).
- **A tab left open:** the key is in each page's memory only while its session is open, and every page forgets it at a lock, the quick exit, a lock or quick exit from another tab, the erase, and when another code is made; an unlock still being worked out when one of these comes opens nothing. A page with a stale key cannot write either: every write checks the code stored in its own transaction (`app/src/data/code-guard.ts`).

### Key hierarchy

- **The code** (4 to 6 digits) is never stored. At each unlock, one PBKDF2-SHA-256 derivation (600 000 iterations, the verifier's random 16-byte salt) gives a 32-byte secret, which is never stored and wiped after use.
- **HKDF-SHA-256 splits that secret** under two labels (`siapso code verifier v2`, `siapso data key wrapping v2`): the **check**, stored as the verifier (`version: 2`), and the **wrapping key**, an AES-GCM 256 key created non-extractable and kept in the page's memory only while the session is open (`app/src/data/vault.ts`). The two outputs are independent: the stored check gives nothing of the wrapping key, and one expensive derivation serves both.
- **Each record written has its own data key**, 256 random bits. The record (JSON) is encrypted with it by AES-GCM, with a new random 96-bit IV; the data key is encrypted (wrapped) with the wrapping key by AES-GCM, with its own new IV. The additional data of both binds the envelope version and the record: `profile:<id>`, `history:<profile id>:<id>` or `contacts:saved` (`app/src/domain/crypto.ts`). A fresh data key and fresh IVs at every write mean that no key and IV pair is ever used twice.
- **One code per phone:** in woman mode it is hers, in accompanied mode the accompanying person's; it wraps every data key the phone holds. Whoever knows the code opens every profile of the phone, by design.
- **Record format:** a profile is stored as `{ id, sealed }`, a history entry as `{ id, profileId, sealed }`, the saved contacts as `{ sealed }`, where `sealed` is `{ v, keyIv, key, iv, data }` in base64url.

### The update from the versions in clear

- The versions before SCRUM-39 kept the records in clear, and their verifier is the PBKDF2 output itself: a key derived from that output would be readable from storage. At the first right code after the update, the app makes a new verifier with a **new salt** (a second derivation, once), seals every record kept in clear with the new wrapping key, and writes the new verifier and the sealed records **in one IndexedDB transaction**, which also checks that the code stored is still the one opened. A failure or a tab closed in the middle leaves the plaintext and the old verifier whole: nothing opens (the code screen says that the profiles could not be opened) and the next right code tries again. A record is never half migrated, and the two forms are never both lost.
- The same transaction makes the verifier again when it has fewer iterations than the app makes: every data key is wrapped again for the new key, and the records themselves are not encrypted again. The app has no other change of code: a forgotten code is erased with everything, and the encrypted data would be unreadable anyway.
- **Invariant: a version 2 verifier means that no legitimate record is in clear.** Records in clear are sealed only in the transaction that replaces a verifier of the format before SCRUM-39, or in the one that stores the first code of a phone from before codes existed (`storeNewCode`, refused when a code is stored). With a version 2 verifier, a record in clear can only have been written into the storage from outside: the readers never show it (a profile or history entry is left out, the contacts are said unreadable and never listed), and the next unlock deletes it, never seals it. A sealed record no key of the code opens (a record of another code, a verifier made again without its key) is left as it is, unreadable, and the pass goes on.
- **Time:** only the storage steps are timed, never the encryption, so a slow phone is never refused for being slow. A read that does not answer in time writes nothing. A write that does not end in time is aborted; it counts as done only if its transaction committed anyway, and after any failure the app reads the stored verifier again and opens with the new key only when its verifier is the one stored. The new key is otherwise dropped.
- An older version left open in another tab cannot open the new verifier, and its writes are refused once the verifier changed. The tabs are told when the verifier is made again, so they lock and ask for the code. A verifier of a newer version of the app is not tried here, and no try is counted.
- An unlock under way when the session is locked (the quick exit, a lock from another tab, the erase, another code), also while it waits for another tab's try, opens nothing; so does a code being made. The code is then typed again.

### What stays visible without the code

- The settings: the language, the mode (woman or accompanied) and whether the welcome is over. The mode says whether the phone is used by a woman for herself or by someone who accompanies women.
- The code's verifier (salt, check, iterations, version) and the code's length (4, 5 or 6, kept since SCRUM-56 so that the code screen tries the code at its last digit), the count of wrong codes and the end of their wait, and the tabs' random marks (`docs/privacy.md`). A verifier kept before the length was gets it at the next right code, in the transaction of the sweep, its salt and check unchanged.
- The random ids of the profiles, history entries and saved contacts; the profile id of each history entry, so the number of results kept per profile (20 at most); the number of records and their sizes, which grow with the length of a pseudonym, the number of situations or items.
- The knowledge pack, which is public, and the times at which the browser writes its own files.

### Limits

- **The code bounds the encryption.** Someone who copies the storage can try every code offline against the stored check, without the waits after wrong codes: 10 000 codes of 4 digits, 1 000 000 of 6 digits, each costing one PBKDF2 derivation at 600 000 iterations. A graphics card goes through every 6-digit code in minutes, a laptop in hours or days. This forensic attacker, with the phone and tools and time, stays out of scope (below); the encryption stops anyone who reads the storage without trying codes, and makes the code, not a glance at the storage, the way in.
- **The code's length is in clear (SCRUM-56, a team decision).** It narrows nothing this attacker cannot already try: a search that tries the shortest codes first goes through every 4-digit code (10 000) before any longer one, so a 4-digit code falls in the same time with or without its length, and a 6-digit code still needs up to the 1 000 000 tries of its length (the 110 000 shorter codes it skips are about a tenth of the search). On the phone itself the code screen tries the code at that count, so anyone who types digits there sees the length; the tries still count, 5 before the first wait. A length changed in the storage from outside makes the code screen try at the wrong count, each try counted as a wrong code: editing the storage is out of scope (below), and replacing the verifier itself would lock her out as surely.
- **Plaintext left behind by the update:** the browser's storage engine may keep the replaced plaintext records, and the old verifier, in its files until it compacts them. A forensic copy taken soon after the update may hold them. The new verifier has a new salt, so the old one gives no key to the sealed data.
- **Memory while open:** the wrapping key and the records of the screens shown are in the page's memory while the session is open. Whoever holds the phone then sees what the app shows, until the two-minute lock or the quick exit. Reading a running browser's memory is out of scope.
- **Deletion and rollback of storage:** someone with the phone can delete records or put back an older copy of the browser's storage, its verifier included; the app cannot tell an older sealed record from a current one. Records written in clear into the storage are never read (above). Editing the storage stays out of scope (below).
- **On screen:** the encryption protects the storage, not the screen. A result names the products checked, and a finding is never hidden (a safety message). The situations of a saved profile, a note on contraception, the situations the base does not read (one section) and, in accompanied mode, the reminders (one section, always there, since the IPTp reminder is left out for HIV with cotrimoxazole) show at a tap only, so that the result of an HIV profile and that of a profile with no situation look the same before any tap, except when SP (sulfadoxine-pyrimethamine) or amodiaquine (ASAQ included) is checked. Two findings also fire on the HIV situation alone (SP with cotrimoxazole, amodiaquine with HIV treatments): with SP or amodiaquine checked, the HIV profile gets their card at a higher level ("before the next dose" where a profile with no situation gets "unknown"), in both modes and at every state of the pregnancy, because the interaction is real. Their messages say it as a condition, never as a fact about her, but the card and its level are there, and someone who has seen SP checked for other women, with no such card, can infer her situation. The team keeps the rules: removing them would harm women on cotrimoxazole, and showing the card to every woman would discourage the routine preventive treatment of malaria (IPTp); the clinical committee is asked about it (`knowledge/README.md`, H-1).

## Knowledge pack

### Tampered pack

Someone changes the pack files, and only them: a CDN or a cache that serves altered or mixed files, a bad deploy that ships pack files that were not signed together, and, in the future, a copy passed from phone to phone.

- `manifest.json` is signed with Ed25519 (`manifest.sig`, over its exact bytes) and every fragment is bound to it by its sha256 and size. The app checks the signature with the public keys built into it before trusting anything in the manifest, checks every fragment it downloads, and validates the whole pack with `parsePack`.
- Nothing is activated before every check has passed, and a refused pack leaves the active one in use. A pack signed by an unknown key, or without a signature, is refused by a release build, and a release build refuses to be made with such a pack.
- Limit: the signature covers the pack, not the app. A host that serves a modified app can ship other keys or no check at all (see "Out of scope").
- Residual risk: none known for the pack content while the private key stays secret. A refused update leaves the phone on its current pack (see "Withheld updates").

### Replayed old pack

Someone serves an older pack, validly signed by the team at the time, to bring back content that was corrected.

- The version is inside the signed manifest. The app never takes a version below the version of the pack built with it (the floor), whatever the state of the phone's storage: first install, cleared data, a storage that does not answer or cannot be read, a stored pack whose key was revoked. Above the floor, it takes only a version strictly above the active pack, and above any version rolled back on the phone; a pack of the same version with other content is refused. The storage checks the versions again inside its transaction. A fragment cannot be swapped for an older one, since its sha256 is in the signed manifest.
- Residual risk: between the floor and the active version nothing older is taken, so a replay can only bring back a pack at or above the version the app was built with. A user who rolls back keeps the previous pack, even below the floor: that is their choice, made in accompanied mode after the code, within the limit below.

### Rollback to a withdrawn pack

Someone, or a hurried accompanying person, goes back to a pack the team has withdrawn because it lowered an alert.

- `minimum-safe-version` in `knowledge/pack.yaml` is written into the signed manifest, so it cannot be forged. A rollback is allowed only to a version at or above the highest minimum safe version known: the active pack's and the one of the pack built with the app; the Status screen hides the button otherwise.
- A pack the user rolled back to that is below the minimum safe version of the pack built with the app is set aside at start: the app pack replaces it and the rollback mark is cleared, even when that brings back the very version the user left. The withdrawal wins over the user's earlier choice, and the phone is never left without a pack.
- Without the field, rollbacks work as before: the team sets it when a pack must never come back.

### A stored pack below the floor is no longer a fallback

This is a deliberate trade-off. When the download fails, the app uses the pack stored on the phone only if it is not below the version built with the app (unless the user rolled back to it, within the minimum safe version). A phone that keeps an older pack and cannot read the pack built with the app (no service worker yet, storage trouble) therefore has no pack rather than an old one: the danger signs and who to call still work, and the Status screen says the base is not available. An old pack can give a lower alert than the current content; saying plainly that the base is missing, so that the woman is sent to a health worker, is the safer failure for a pregnant or breastfeeding woman than a confident answer from withdrawn content. In normal use the service worker serves the pack built with the app, so this case is rare.

### Withheld updates

Someone blocks the pack download, so that a phone keeps an old pack.

- The app keeps working with the pack it has, and every result shows the knowledge base version and date. There is no expiry date.
- Accepted risk: availability is not protected; a network attacker can always withhold traffic.

### Compromised signing key

The private key leaks.

- The private key never enters the repository: the release key is generated by `siapso-pack keygen`, which writes it to a file (never to the screen), refuses any path inside a repository (links and Windows junctions resolved), and is kept offline; the repository holds only public keys. CI does not sign: a repository secret is readable by anyone with push access, through a workflow change, so signing will come with the release workflow and a protected environment.
- Each key has a `keyId`. Removing a key from `app/src/config/pack-keys.ts` and releasing the app revokes it: the app then refuses every pack that key signed, the one stored on the phone included, and takes a new signed pack (never below the version built with it). Rotation steps are in `docs/pack-signing.md`.
- Residual risk: a phone keeps trusting a revoked key until it takes the app update (the app asks before it updates). On Windows the key file is not made private to its owner: it must live on an encrypted drive, never in a synced folder.

### Unsigned test and demo builds

A demo build (`pnpm build`, Vite mode `demo`, with `VITE_ALLOW_UNSIGNED_PACK=true` from `app/.env.demo`) accepts an unsigned pack, or one signed by a key it does not know, so the signature protects nothing in it (a bad signature from a listed key is still refused, and the version and hash checks still apply).

- Limits: the flag counts only outside production mode, and only with the exact value `true`. Every build that does not accept unsigned packs (`pnpm release:build`, or any mode without the flag) fails when no public key is listed or when its own pack is not signed by a listed key, and a production build fails when the flag is set, so a release that silently accepts unsigned packs, or that would refuse every pack, is never produced by mistake.
- A demo build cannot pass for a release: it goes to `app/dist-demo`, never to `app/dist` where a release goes; its `build-info.json` marker says `"mode": "demo"` and `"acceptsUnsignedPack": true`, and `pnpm release:build` checks the marker of the release before it reports success; it prints a warning at build time; and its Status and About screens say "Version de test : base de connaissances non signée." whatever the pack in use. CI makes demo builds only and never publishes them. A release build refuses a pack that a demo build stored on the same phone and downloads a signed one.
- Risk: a demo build given to real users would accept any pack served from its origin; the screens say it is a test version. The v0.1.0 demo may be a demo build (its content is not clinically validated); the MVP release must be signed.

## Prescription reading (SCRUM-57)

### An untrusted PDF or photo

Someone hands over a crafted PDF or image (a "prescription" from a messaging app) to break the parser, run code or make the phone fetch something.

- The file is read only in the reading worker (`@siapso/ocr`), never by the page: its first bytes say what it is (never its name or type), a file of more than 20 MB or a photo of more than 40 megapixels is refused before it is decoded, and anything that is neither an image nor a PDF is refused.
- pdf.js 6.4.299 opens it from the bytes given (no URL), in that worker (no worker of its own), with no XFA, no font faces, no system fonts, no worker fetch and no cMap, standard font or ICC address. Its WebAssembly decoders of scanned images (JBIG2 and CCITT fax, from PDFium; JPEG 2000, from OpenJPEG) are files of the pack, which pdf.js reads through the factory the worker hands it (`packDecoders`): from the Cache API only, and any other file it asks for (a cMap, a font, its colour or script engines) is refused. When a decoder fails, pdf.js imports a JavaScript fallback from its `wasmUrl`, which is set to an address with an unknown scheme (`siapso-ocr-pack:`): the import fails at once, with no request, and that image is left out. pdf.js also compiles a PostScript function of the file to WebAssembly in memory. This version has no `eval` path and no `isEvalSupported` option (checked in its build), and no script ever runs: the pack carries no `pdf.sandbox` and no annotation or form layer is drawn. A password, a damaged file and a page that cannot be parsed are refused with their own reason. Three pages at most are read.
- Image sizes, so that a file of a few kilobytes cannot make pdf.js decode hundreds of megabytes (`oversizedImage` in `ocr/src/pdf-images.ts`, then `readPdf`, tested). pdf.js's own `maxImageSize` only checks the width and height a painted image's dictionary gives: a soft mask (`/SMask`), a stencil mask (`/Mask`) and the JPEG or JPEG 2000 data of an image are decoded at their own size. So before pdf.js reads anything, the file's bytes are read: every dictionary followed by the `stream` keyword, read from the start of the file as pdf.js reads tokens (whitespace, comments, strings, nested dictionaries, `#xx` name escapes, malformed entries skipped), stream data skipped, with no cross-reference table trusted, and also every dictionary that ends right before a `stream` keyword this reading did not reach (inside another stream's data, say). The file is refused as too large (`too-large`) when any of them gives a width times a height (`/Width` or `/W`, `/Height` or `/H`, the largest when given twice) of more than 20 megapixels, whether or not it says `/Subtype /Image` (a mask need not); a mask that gives one side only is counted with the largest side of the file; a size given by an indirect object is followed when that object is written plainly (`N G obj 6000 endobj`, every such header indexed in one pass); the JPEG frame size or the JPEG 2000 SIZ size of an image whose first filter is `DCTDecode` or `JPXDecode` is read too. When no size is too large but one cannot be read, the file is refused as one that cannot be read safely here (`pdf-unsupported`): a size or a filter given by an object that cannot be read (in an object stream, missing, not a number), a JPEG or JPEG 2000 filter after another filter, a JPEG height left to a later marker, a `stream` keyword right after `>>` with no dictionary found within 64 KB before it, nesting deeper than 1,000 levels, and a file that takes more than its work budget to read. The budget (8 million steps and 1.5 a byte, every scan and every lookup counted) has the slowest files to read (a token or a stray `stream` keyword every few bytes) refused or read within 1.5 s for 20 MB on the bench laptop, about 6 to 9 s on a phone four to six times slower, inside the 90 s of a reading; the scanner-like, Word-like and Chromium-printed files tried take 0 to 4 ms. Then pdf.js leaves out any image whose dictionary gives more than 20 megapixels (`maxImageSize`), which covers inline images and inline stencil masks in content streams, which the bytes do not show when compressed; its warning refuses the PDF rather than a reading with a page missing. Not enforced: the JPEG data of an inline image is decoded at its own frame size; in an encrypted file the JPEG and JPEG 2000 data are not read (only its dictionaries are in the clear); JBIG2 and CCITT data are decoded inside their WebAssembly decoders at the size their data gives, their output at the size of the dictionary (checked); and a file crafted for this reading and pdf.js to find different dictionaries (a stream dictionary of more than 64 KB where the reading from the start does not reach it, holding a smaller dictionary that ends at the same `stream`). Such a file can at worst take the tab's memory: the reading is then lost, not data.
- What the worker enforces, from its start and before any message (`closeNetwork` and `guardedFetch` in `ocr/src/runtime.ts`, tested): its `fetch` refuses every address until a reading names the pack, then answers only the pack's files from the Cache API and refuses every other address, a blob address included; `XMLHttpRequest`, `WebSocket`, `EventSource` and `WebTransport` throw when made, and `importScripts` throws. What it does not enforce: a module import of an address (`import()`), and the workers ONNX Runtime starts for its threads (from its loader, a blob address of the pack's file, revoked once the models are loaded). The code that runs there gives neither an outside address: pdf.js and the ONNX Runtime loader are imported from blob addresses of the pack's files, and pdf.js's only import of an address is the fallback above. So a request out of the worker needs a bug that runs code of its own, not a parser that misreads a file.
- Residual risk: a memory-safety bug in the browser's image decoders, in the WebAssembly runtime or in pdf.js's WebAssembly decoders. The worker is ended after a reading that does not finish within 90 s and a few minutes after the last reading.

### A tampered reading pack

Someone serves altered model, runtime, pdf.js or decoder files. Every file of the pack is checked by size and SHA-256 against `ocr-pack.json` once stored, and a file that differs is dropped. The manifest itself is not signed: like the voice pack, the pack is served from the app's own origin, so the host's integrity protects it (see "Out of scope"); signing it as the knowledge pack is would be a later step. A wrong model can only misread text: every product read is confirmed by her, and the engine alone sets the level.

## Out of scope

- A forensic attacker with the phone and unlimited time, including one who edits the app's storage on the phone or tries every code offline against a copy of it (see "Personal data on the phone", Limits).
- A compromised build machine or web host that serves a modified app: the signature protects the pack, not the app code, which can carry other keys. The deployment's host and access control protect the app.
- The evaluation API (`server/`), which reads `pack.json` from the team's own build; `pack.json` is not signed and the app never reads it.
- Denial of service against the download (see "Withheld updates").
