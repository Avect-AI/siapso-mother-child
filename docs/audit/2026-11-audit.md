# Pre-publication audit, November 2026

Nothing was published, no history was rewritten and the visibility of the repository was not changed: those are decisions for the team, and the exact steps are at the end of this page.

This report never quotes a secret, a key, an address, an IP address or a phone number. A finding names the check, the kind of match, the path and the commit, so that it can be reviewed in place.

## How to run the audit

The audit is `tools/release/audit.sh`. It is run by hand before publication and again at each release (Task 22, SCRUM-36). Its fixture test, `tools/release/audit.test.sh`, runs in CI.

```sh
# What GitHub serves: every branch, tag and pull request ref (the reference run)
sh tools/release/audit.sh --published

# Every ref of the local clone
sh tools/release/audit.sh

# Some checks only
sh tools/release/audit.sh --published --only secrets,personal-data
```

- **Checks**: `secrets`, `licences`, `sources`, `personal-data`, `large-files`, `file-names`, `identities` (information only). All run by default.
- **Exit code**: 0 when there is no finding, 1 when there are findings, 2 on a usage or tool error (download, checksum, git).
- **Needs**: git, awk, curl or wget, sha256sum (or shasum, or openssl), tar (and unzip or Python on Windows), Python 3 when `reuse` 6.2.0 is not installed, and the network on the first run. `--published` clones the remote `origin` with your git credentials.
- **Cache**: `.cache/audit/` at the root of the repository, git-ignored (`AUDIT_CACHE` changes it). It holds the gitleaks release archive, the `reuse` virtual environment and the mirror clone. It can be deleted at any time.
- **gitleaks**: version 8.30.1 (published 2026-03-21). The script downloads the release archive for the platform (Linux and macOS, x64 and arm64; Windows x64) from the GitHub release, and checks its SHA-256 against the value pinned in the script before every run. A mismatch stops the audit. The binary is extracted into a temporary folder of the cache for the run and never committed. `AUDIT_GITLEAKS_BASE_URL` points to a mirror of the release files; the pinned checksums still apply.
- **reuse**: the version pinned in `tools/reuse/requirements.txt` (6.2.0). A `reuse` command of that version on the `PATH` is used; otherwise it is installed into the cache. On Windows, `reuse` can fail on the long paths of `node_modules`; run the licence check on Linux (CI does it on every pull request) or on a clean export of the tree.
- **Accepted findings**: the function `accepted()` at the top of the script lists every reviewed finding with its reason, as a pattern over the check, the kind, the path and the detail. Secrets are pinned to their commit and line, the other content findings to each commit that adds them, so a new match in the same file is still reported. The list below (A1 to A6) explains each one. Add an entry only after a review, with its reason, and record it in the audit report of the release.
- **Output**: one `FINDING [check] kind: path (detail)` line per finding (for the content and file name checks, one per commit that adds the match, named in the detail), a summary per check, and `Result: no finding.` or `Result: <n> findings.` The matched values are never printed.

## Scope and method

The reference run used `--published` on 2026-11-05: a mirror clone of the GitHub repository, with **321 commits** reachable from **6 branches and 54 pull request refs** (no tag), this branch included, after the merge of `main` at `af39dfb` into it (`b766c91`). The figures of this report are those of that run; the commit that records them is the only one added after it, and a run on it gave the same result. Pull request refs (`refs/pull/<n>/head`, and `refs/pull/<n>/merge` while a pull request is open) are kept by GitHub after a branch is deleted and cannot be deleted by the owners: they become public with the repository, like the branches.

Every file of every commit was added, line by line, by that commit or one of its ancestors. The content checks therefore read every line added by every commit of every ref (`git log -p`, renames read as additions, a merge read against its first parent, so that what only a merge adds is read too): this reads the tree of every commit once.

## Decisions for the team

**D1. The French commits (L1).** Recommended: keep the history as it is. Rewriting `main` changes every commit identifier, breaks the links between the pull requests, the commits and the Jira tickets, and does not remove the old commits: the pull request refs keep them readable until GitHub Support purges them. The only clean rewrite is to publish a new repository with a rewritten history and archive this one, losing the pull request history. If the team does that, do it once for D1 and D2 together.

**D2. The email addresses (M1, M2).** For the future, whatever is decided for the past:

1. On the account `2sml001`: GitHub, Settings, Emails, turn on "Keep my email addresses private" and "Block command line pushes that expose my email". From then on, the commits GitHub makes for the account (squash merges through the web or the API, including `gh pr merge` used by `tools/github/merge-pr.sh`, and web edits) carry its `<id>+2sml001@users.noreply.github.com` address. The setting does not change existing commits, and does not change commits made on a computer: those use the local git configuration.
2. Each developer sets their GitHub noreply address in git (`git config --global user.email "<id>+<login>@users.noreply.github.com"`). `git commit -s` then signs off with the same address, which the Developer Certificate of Origin check requires.

For the existing history, the developer of M1 decides whether their personal address may become public with the repository (as in most open source projects), and the team decides for the account address (M2). If either must not be published, the only remedy is the new repository of D1 with the addresses rewritten (`git filter-repo --mailmap`); a `.mailmap` file changes how git displays a name, not what the commits contain.

D1 and D2 remain decisions for the team. D3 and D4 were decided on 2026-11-05 and applied in this pull request.
