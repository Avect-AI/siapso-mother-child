# Plan F: MVP features after the demo

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Signed knowledge packs with light updates, encrypted profiles on shared phones, QR transfer between health workers, adverse event reports, the evaluation API with proven parity, a DHIS2 aggregate export, a plan and scripts for a lighter voice model, and a full audit before the repository becomes public.

**Architecture:** Spec section 9 of `docs/superpowers/specs/2026-11-03-implementation-design.md`. Everything runs offline on the phone except the optional API and the export files. Cryptography uses WebCrypto (PBKDF2, AES-GCM, SHA-256) and `@noble/ed25519@3.2.0` with `@noble/hashes@2.4.0` for signatures.

**Tech Stack:** as in Plan C, plus Node's `node:http` for the server (no framework), `@noble/ed25519`, `@noble/hashes`, a QR encoder and decoder (pick small, maintained, MIT or Apache packages published on or before 2026-10-20, for example `uqr` for encoding and `jsqr` for decoding; justify the choice in the PR).

## Global Constraints

- Same as Plan C.
- Private keys never enter the repository: the pack signing private key lives in a GitHub Actions secret for CI builds and in an offline file for releases; the repository holds only public keys. Tests use keys generated at test time.
- Threat model documented in `docs/threat-model.md` (created in Task 24, extended by later tasks): casual access on a shared phone, tampered pack, replayed old pack, lost phone; out of scope: forensic attacker with the device and unlimited time.
- No identifying data leaves the phone without an explicit action and consent; the server never accepts identifying fields.

### Task 23 (SCRUM-38): signed packs and incremental updates

Branch `feat/SCRUM-38-signed-packs`.

**Files:** `tools/knowledge/src/sign.ts` (+ test), `tools/knowledge/src/cli.ts` (`siapso-pack sign --key <file>`; `build` writes an unsigned manifest; CI signs with the secret `PACK_SIGNING_KEY` when present), `app/src/data/pack-verify.ts` (+ test), `app/src/data/pack-loader.ts` (verify before activation; refuse lower versions; fragment-level update by hash; keep previous pack; rollback), `app/src/config/pack-keys.ts` (public keys), `tools/knowledge/src/keygen.ts` (prints a new key pair; never writes the private key inside the repository), `docs/pack-signing.md`, `CHANGELOG.md`.

**Format:** `manifest.json` unchanged plus `manifest.sig` (base64 Ed25519 signature over the exact bytes of `manifest.json`); `keyId` in the manifest selects the public key.

**Behaviour:** the app refuses a pack whose signature does not verify with a known key, or whose version is lower than the active one (semver compare), or whose fragments do not match their hashes; it downloads only fragments whose hash differs from the active pack; it keeps the previous pack and can roll back (Status screen action in accompanied mode). Development builds without a key: the app accepts an unsigned pack only when built with `VITE_ALLOW_UNSIGNED_PACK=true` (default false in production builds; tests cover both).

- [ ] Steps: tests first (sign and verify round trip, tampered manifest, unknown key, lower version, partial update, rollback); implement; add the CI secret instructions; PR `feat: sign knowledge packs and update them by fragment`, `Refs: SCRUM-38`.

### Task 24 (SCRUM-39): encrypted profiles

Branch `feat/SCRUM-39-encrypted-profiles`.

**Files:** `app/src/domain/crypto.ts` (+ test), `app/src/data/profiles.ts` (encrypt at rest), `app/src/state/session.tsx` (hold keys in memory only while unlocked), migration of existing plaintext profiles, `docs/threat-model.md`, `CHANGELOG.md`.

**Scheme:** each profile has a random 256-bit data key; profile data is encrypted with AES-GCM (random 96-bit IV per write); the data key is wrapped with a key derived from the unlock code (PBKDF2-SHA-256, 600 000 iterations, random 16-byte salt). In accompanied mode the accompanying person's code wraps every data key she holds; in woman mode the woman's code. Contraception history and HIV-related conditions are hidden by default on screen and revealed by an explicit tap. Auto-lock after 2 minutes clears keys from memory. Migration encrypts any plaintext profile at the first unlock and deletes the plaintext.

- [ ] Steps: tests first (round trip, wrong code fails, IV uniqueness, tamper detection, migration, lock clears keys); implement; PR `feat(app): encrypt profiles on the phone`, `Refs: SCRUM-39`.

### Task 25 (SCRUM-40): QR transfer in accompanied mode

Branch `feat/SCRUM-40-qr-transfer`.

**Files:** `app/src/domain/qr-payload.ts` (+ test), `app/src/screens/QrShare.tsx`, `app/src/screens/QrScan.tsx` (+ tests), `app/src/i18n/*`, `docs/qr-transfer.md`, `CHANGELOG.md`.

**Payload:** `SIAPSO1:` + base64url(salt 16 bytes, iv 12 bytes, AES-GCM ciphertext of the minimal profile JSON: pseudonym, term input, breastfeeding, conditions, long-term items), key from a 6-digit transfer code shown once to the sender and told to the receiver orally (PBKDF2 600 000). Size checked against QR version 25 at error correction M; the minimal profile must fit. Scanning uses `BarcodeDetector` when available, otherwise the JavaScript decoder on camera frames; camera permission refusal falls back to explaining that the transfer needs the camera. A printable card layout (CSS print) for the mother-child health booklet.

- [ ] Steps: tests first (encode and decode round trip, wrong code, oversize refusal, payload contains no field outside the minimal set); implement; PR `feat(app): transfer a profile by QR code`, `Refs: SCRUM-40`.

### Task 26 (SCRUM-41): adverse event reports

Branch `feat/SCRUM-41-adverse-events`.

**Files:** `app/src/screens/Report.tsx`, `app/src/domain/report.ts` (+ tests), `app/src/data/reports.ts`, `docs/adverse-event-reports.md`, `CHANGELOG.md`.

**Behaviour:** from a result, "Signaler un effet observé": product or remedy (from the check), pregnancy term or breastfeeding, event (short free text and a checklist of common events), date, seriousness (needed hospital care, yes or no); no causality question. Explicit consent of the woman (checkbox read aloud by the accompanying person). Stored encrypted with the profile; exported on demand as JSON and CSV in a documented provisional format marked "format to be confirmed with ARP (national vigilance centre, decree 2023-2423)". Never sent automatically; the screen never says that the report was received by anyone.

- [ ] Steps: tests first; implement; PR `feat(app): record adverse event reports for later sending`, `Refs: SCRUM-41`.

### Task 27 (SCRUM-37): evaluation API with parity

Branch `feat/SCRUM-37-evaluate-api`.

**Files:** `server/` package (`@siapso/server`): `src/server.ts` (node:http), `src/routes.ts`, `src/auth.ts` (API keys from a JSON file of SHA-256 hashes given by path in an environment variable; constant-time comparison), `src/quota.ts` (fixed window per key, in memory), `src/validate.ts` (request schema with `additionalProperties: false`; no identifying field accepted), `openapi.yaml` (OpenAPI 3.1), tests including `test/parity.test.ts` (every reference case through HTTP and through the library: deep-equal outputs), `Dockerfile` (Node 24 slim, non-root user), `docs/api.md`, root script `server:start`, `CHANGELOG.md`.

**Endpoints:** `GET /v1/health`, `GET /v1/pack` (version, date, counts), `POST /v1/evaluate` with `{ pack_version, context }`, answering 409 when `pack_version` differs from the loaded pack, 401 without a valid key, 429 above quota, 400 on invalid input with the error path, 200 with the engine `Evaluation`.

- [ ] Steps: tests first; implement; PR `feat(server): add the evaluation API with parity tests`, `Refs: SCRUM-37`.
